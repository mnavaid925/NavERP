- **`engine_label` is a VALIDATED string, not a ContentType FK.** A label naming no model is refused at

add an explicit `order_by`. Hit this on two list views.

### Two probing findings that made the delivery board honest
- **`procurement.DeliverySchedule` is NOT a message delivery** — it's physical goods
  (`planned/confirmed/shipped/received`). A name-matching scan would have counted logistics as
  notifications. Excluded with the reason.
- **`simulated` is a distinct bucket, not a success.** crm/scm/projects webhook deliveries carry it and
  it means a DRY RUN — nothing left the building. Folding it into "sent" would let a workspace that has
  never sent anything report a 100% success rate. Real data: 2 sent / 11 pending / 1 failed /
  **2 simulated**, honest rate 66.7%.

### THE BUG WORTH REMEMBERING — an unchecked checkbox is not submitted
**The self-service preference page could only ever opt IN.** Unticking a box submitted nothing, the
view skipped the field, no row was created, and the rule default silently kept applying — the page
*looked* like it worked while doing nothing in the one direction a preference exists for. **Fix: emit a
hidden `<input value="off">` BEFORE the checkbox**; an unchecked box then submits "off" and a ticked one
submits "on" after it (`.get()` returns the LAST value for a repeated key). This is a general HTML trap,
not a Django one, and it applies to every checkbox-as-opt-out form in the repo.

Two smaller ones: `{"%s__in": ...}` as a **dict key** is not a format string (the lookup was literally
on a field named `%s` — build the key by concatenation), and a **flat context list** fed to a
`{% for a, b in x %}` filter raises "Need 2 values to unpack".

### ENVIRONMENT — the repo has a `post-commit` hook that breaks `&&` chains
`.git/hooks/post-commit` prints `git status` and **exits non-zero**. It does not block the commit, but it
stops any `&&` chain right after `git commit`, which made two long commit chains look like they had
failed when every commit had in fact landed (verify with `git log`, not the exit code). **Use `;`
between commit steps, or one commit per call.**

### The real find: `temp/audit_integrity.py` check 6 was WRONG
Closing the plan needed check 6 to pass and it was failing — on `core.SensitiveFieldMask`, plus four
of my own 0.8/0.10/0.11 models. **The seeders were fine; the CHECK was wrong.** It read only
`apps/<app>/management/commands/seed_<app>.py`, so it reported a model as unseeded when that model is

what the check exists to catch. Exemptions now documented: `SensitiveFieldMask` (cross-app),
`DisposalRecord` (evidence of a real disposal), `SettingValue` (absence = taking the default),
`CustomFieldValue` (no record to attach to), `BusinessRuleLog` (an evaluation log),
`ProjectReportRun` (a report execution record, 7.16's).

**`temp/` is gitignored — 0 tracked files.** So the audit fix lives locally by design and cannot be
committed; it takes effect for every future run. Worth remembering: the audit itself can be the bug,
and a failing check is not automatically a failing codebase.
