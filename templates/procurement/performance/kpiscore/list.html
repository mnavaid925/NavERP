Every measured line in the workspace, across every period. A line is written by supplierevaluation_generate — never by hand — so THERE IS NO CREATE BUTTON HERE and no supplierkpiscore_create route: a hand-created line would be a measurement with no computation behind it. The header actions point at where lines actually come from. Context contract (crud_list + extra_context), and NOTHING else exists here: object_list, page_obj, q, band_choices, source_choices, kpis, scorecards, stats{total, ok, warning, critical, unknown}. The view's crud_list filter tuple is exactly (("band","band",False), ("source","source_at_time",False), ("kpi","kpi_id",True), ("scorecard","scorecard_id",True)) with search_fields=("kpi_name","comment","scorecard__number","scorecard__party__name") — so the filter bar offers exactly q, band, source, KPI and period. kpi and scorecard post pks and compare with |stringformat:"d" (never |slugify); band compares against SupplierKpiScore.BAND_CHOICES. source_at_time is a plain CharField with NO choices, so crud_list's enum guard bails out and the raw GET value reaches .filter(). That is safe — junk matches nothing — but it means the dropdown below is the only thing keeping the offered values legal, which is why it is pinned to SupplierKpi.SOURCE_CHOICES (context key source_choices) rather than invented here. For the same reason the register has no get_source_at_time_display: the three values are spelled out in an explicit chain with an else-fallback that prints the raw value. Badge classes are COLOUR-NAMED only (L33). Bands take their class from obj.band_css — the committed BAND_CSS mapping on the model — so a row can never disagree with the model about what "critical" looks like. Edit appears ONLY on a manual-entry line: a derived or survey line is recomputed by Generate from evidence, and typing over it would leave a number nobody stands behind. The button is the UX half of that rule; the VIEW is the authorization boundary. Delete is @require_POST, so it can only be a form. {% endcomment %}
