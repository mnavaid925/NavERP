THIS IS THE HAND-RAISE PATH, for what no rule can see: a tip-off, a pattern somebody noticed, a relationship the system has no column for. It writes into the same register the scan does on purpose, so a human finding and a machine finding get the same triage, the same disposition vocabulary and the same audit trail. The form carries exactly: rule, severity, document_date, amount, detail, matched_on, assigned_to, and the seven source pointers. Everything the SYSTEM or the WORKFLOW owns has no input here and cannot be posted: tenant and number (system-stamped), dedupe_key and detected_at (detection's), and status / resolution_note / resolved_by / resolved_at / suspension (moved only by the four verb methods on the model). `severity` IS on the form on purpose — it is a default a rule stamped, not a verdict, and a reviewer has to be able to re-grade a row the engine over-called. Field help is keyed off field.name so it stays correct if the field order changes, and each label is bound to its widget with for="{{ field.id_for_label }}". {% endcomment %}

{% if is_edit %}What amending does{% else %}What happens when you save{% endif %}

{% if is_edit %}

Saving changes the alert and nothing else. An alert can only be amended while it is still open: once it has been substantiated, marked a false positive or referred on, it is the record a decision rests on, and the honest way to correct it is to raise a new alert with the new evidence.

{% else %}

Saving files the alert as open and takes you to it. It joins the same register the rules write into and gets the same four dispositions, so nobody reading the board has to know whether a row came from a person or from a rule.

{% endif %}

Nothing else happens. Raising an alert holds no purchase order, blocks no payment, refuses no award and never edits, merges or deactivates a supplier record. The only place a vendor is actually blocked is the vendor suspension register, and that stays a separate, deliberate decision made by somebody who can defend it.
