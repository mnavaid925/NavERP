Field help is keyed off field.name so it stays correct if the form order changes, and every {% if %} branch falls through to field.help_text — the model's own help text is already written and a silent blank would be worse than a duplicate. The ABC gotcha gets its own explainer card rather than a line of help text, because it is the one thing on this form that is actively misleading if skimmed: two different models in this system have an `abc_class`, they mean unrelated things, and this filter reads the reorder rule's. {% endcomment %}

Which ABC class is this?

two models, same three letters

This filter reads the reorder rule's ABC class — the uppercase A/B/C revenue rank that SCM's demand planning assigns to an item at a location, where A is the small handful of items most of the money runs through.

It is not the location's ABC class, which is a lowercase a/b/c bin-velocity attribute describing how often a picker walks to that bin. The two are unrelated, and filtering by the wrong one would quietly plan the wrong items.

What happens next

nothing, until you ask
  1. Create the run — this form. It starts as a draft with no lines.
  2. Generate on the run reads every active reorder rule in scope, nets off stock on hand, open purchase orders and open requisitions, and proposes what is still short. Press it as often as you like: each press replaces the previous lines rather than adding to them.
  3. Decide each line — accept, snooze with a date, or dismiss. The decision is kept, which is the whole reason this run exists as a record rather than a screen.
  4. Release turns the accepted lines into one draft requisition per vendor. Approval routing, the budget check and purchase-order conversion all still run afterwards.
