This is a CUSTOMER surface, not a staff one: every link points at another portal route, and nothing here reaches the staff side of scm (no scm:overview breadcrumb, no portalorderinquiry_list, no salesorder_detail). The staff twin of this form is templates/scm/portal/portalorderinquiry/form.html and the two are deliberately NOT the same page — that one carries portal_account and invoice, which a customer may not name. CONTEXT this page may read, and nothing else (the view pins the same list in its module docstring): form — PortalInquiryCustomerForm, bound on POST. SIX model fields only: sales_order sales_order_line shipment inquiry_type requested_resolution quantity_affected — plus the two non-model case fields subject / description. There is no portal_account field and no invoice field ON PURPOSE (naming another account is the whole attack; an invoice picker would offer a document can_view_invoices may not entitle this customer to see at all). is_edit — ALWAYS False. The portal files inquiries and never edits them, so the one branch below on it exists to honour the key, not because an edit path exists. kb_articles — list of dicts. Keys, EXACTLY: `title` and `url`, and no others — built by _kb_articles() in the view, which turns each published+external crm.KnowledgeArticle into its crm:kb_public URL. `article`, `name`, `link` and `public_token` are NOT keys here; a guessed one renders a row of blank links on a 200 page (L41). [] for a workspace with no KB, which is most of them at first, and the whole block is then omitted rather than shown empty. prefill_order — a SalesOrder MODEL object or None (re-resolved against this customer's own orders by the view, so it is never a pk the URL merely claimed). account customer access can_track_shipments can_view_invoices can_view_documents can_raise_inquiries can_request_returns show_credit_and_balance The KB block is ABOVE the form deliberately — the Zendesk / Salesforce deflection pattern. A customer who finds their answer costs nobody a ticket, and an answer offered AFTER the form has been filled in is not a deflection, it is an insult. Each article opens in a new tab so a half-typed question is not lost. `url` is used as an href and never printed: it carries the article's public token, and a credential is a link, never a label. THE CASE IS OPENED SERVER-SIDE and this page says so in words. PortalOrderInquiry.open_for() is the single writer of the crm.Case — it derives the case type from the inquiry type, forces origin="portal", sets the account to the resolved party and picks up the workspace's default SLA policy, all in ONE transaction with this row. There is therefore no case field, no priority field and no "who is this for" field to render: everything about the ticket other than the two boxes below is derived, and a refused submission leaves no orphaned ticket in the CRM queue. Refusals arrive as FIELD errors wherever the customer form has that field, so each renders through partials/form_field.html. form.non_field_errors is rendered at the top because the view re-homes any refusal keyed on a field this narrower form does NOT carry (`invoice`, which only staff may attach) onto the form as a whole — add_error("invoice", …) on a form without that field raises ValueError, which is a 500 where a validation message belongs. SalesOrder carries no *_css property, so the one status chip below mirrors the shipped scm/portal/customer_orders.html chain exactly rather than inventing a third colour scheme. Badge classes are colour-named only — badge-green / badge-red / badge-amber / badge-info / badge-muted / badge-slate. badge-success / badge-danger / badge-warning do not exist in theme.css and render completely unstyled (L33). Everything on this page is user-typed or staff-typed — an article title, an order number, the customer's own name — so it renders escaped and there is no |safe anywhere. A derived figure with no input prints an em-dash and never a 0: an order with no total recorded is not an order worth nothing. No pagination (the view passes no page_obj), no destructive action, and therefore no confirm() dialog on this page. {% endcomment %} {% block title %}{% if is_edit %}Edit Your Question{% else %}Ask Us a Question{% endif %}{% endblock %} {% block content %}
