The stored credential is a marker, not a secret you can use. What is kept is the first few characters plus a one-way hash — enough to answer "is a credential registered, and is it still the same one", and nothing more. That is a correct trade here and only here, because this pass ships no transport: nothing signs a payload and nothing authenticates to a provider, so there is no operation the plaintext is needed for and keeping it would be pure liability.

The day real calls are built, this is a wall and not a detail. A signing key has to be used to sign and a provider credential has to be replayed to authenticate; a hash can do neither, mathematically. The move at that point is to migrate to encryption at rest — a reversible envelope whose key lives outside the row — and specifically not to quietly turn the column back into plaintext because the hash "does not work".

The endpoint address is not fetched by anything. Outbound HTTP is deferred across the whole of 4.19, and when it is built the first thing it needs is not a client library: it is an allow-list plus a private-address block covering RFC1918, loopback, link-local and IPv6 unique-local ranges, re-resolved at request time so a hostname cannot answer publicly once and privately the second time. A tenant-editable URL the server fetches is server-side request forgery by definition, and that guard is the feature rather than an afterthought.
