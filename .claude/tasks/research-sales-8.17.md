### Cross-product consensus (industry-standard shapes)
1. **Trigger → Criteria → Action(s), with ordered steps**: every leader models automation as an event on a target entity, a bounded condition set, and an ordered list of actions (Salesforce flows, HubSpot, Zoho workflow rules, Pipedrive, Odoo, Freshsales blocks). NavERP already has this shape twice (`crm.WorkflowRule`, `sales.LeadRoutingRule.conditions` bounded-JSON pattern).
2. **Process-as-state-machine vs rule-as-reactor**: Zoho Blueprint and Dynamics BPF enforce stage order and mandatory transition data; workflow rules merely react. A sales "process definition" with ordered steps + versioning covers the designer bullet without a graphical canvas runtime.
3. **Multi-tier approvals with per-tier decision rows**: Salesforce approval steps + Power Automate sequential/parallel chains + procurement's own `RequisitionApproval` all agree: one immutable decision row per tier, snapshotted chain length, actions on approve/reject, delegation and timeout escalation as extensions.
4. **Routing modes are a closed set**: fixed owner, round robin (race-safe cursor), weighted, load/capacity-balanced, territory-based, skill-based, with fallback owner and SLA reassignment (LeanData/Q-Assign/Freshsales). 8.1 already implements fixed/territory/round-robin for leads; 8.17 extends the mode set to opportunities/cases.
5. **Alert engines are trigger definitions + fired-alert records**: inactivity timers ("no activity for N days"), stage-change watchers, milestone celebrations (HubSpot, monday, Salesforce). Delivery is a separate channel layer — NavERP's is `core.Notification*` + `sales.MobileDealAlert`.
6. **Dedup is detection → rule → merge**: matching rules define duplicates, duplicate rules decide block/alert at save, jobs scan in batch, merge picks a master and re-parents children (Salesforce). NavERP has detection events (`PartyEnrichmentEvent` kind `duplicate_check`) but no cluster/merge records.

- **Milestone/celebration alerts** — deal won, quota attainment, biggest-deal badges · seen in: *monday CRM, HubSpot, 8.16 `attainment_milestone`* · priority: `differentiator` · spine: `alert_type` choice; reads 8.10 `CommissionEarning`/8.4 forecast data · buildable now.

### 4.5 Data Enrichment & Cleansing
- **Auto-update of missing fields** — propose field fills from provider/import/manual sources with apply/reject review · seen in: *Salesforce (Data.com-style enrichment), Freshsales, ZoomInfo-class tools* · priority: `table-stakes` · spine: **already built — `sales.PartyEnrichmentEvent` (8.3)** with bounded `changes` JSON, per-kind field whitelists, `match_confidence`, consent-purpose FK. 8.17 adds no table; the process designer may invoke it as a step type · buildable now (reuse).
- **Duplicate detection rules & candidate scans** — matching criteria (email/phone/name similarity) producing scored duplicate clusters · seen in: *Salesforce matching rules + duplicate jobs, Zoho dedup* · priority: `table-stakes` · spine: detection events already loggable as `PartyEnrichmentEvent(kind='duplicate_check')`; a `SalesDuplicateCluster` record table (cluster + candidate rows + confidence) does NOT exist anywhere (verified §1.3) · **recommend defer to a later pass / gaps file** (5th model busts the 4-model cap; enrichment half of the bullet is already covered).
- **Merge workflow with master-record pick & re-parenting** — merge up to N duplicates, choose master, field-level pick, children re-parented, merge audit · seen in: *Salesforce merge (up to 3, master pick), OneMerge cross-object* · priority: `common` · spine: would need `SalesDuplicateMerge` + re-parent updates across `crm.Lead`/`core.Party` children · **defer** (§7) — highest-risk write path in the module, deserves its own pass with a contract.
- **Cleansing jobs (batch validation/normalization)** · seen in: *Salesforce duplicate jobs, Odoo scheduled actions* · priority: `differentiator` · spine: `core.JobScheduler.JobDefinition` registration · defer with merge workflow.

### 4.6 Beyond the bullets (seen in leaders, not in NavERP.md 8.17)
- **Re-enrollment / loop protection** (HubSpot) — cap how many times one record can re-enter a process: `max_enrollments` field on `SalesProcessDefinition`; cheap, include it. priority: `common` · buildable now.
- **Process execution log** (crm has `WorkflowLog`; projects has `WorkflowExecutionLog`) — an append-only fire record per process run. Fold into `SalesApprovalDecision` + `core.AuditLog` this pass; a dedicated `SalesProcessRun` table is the natural 5th model → defer. priority: `common`.
- **AI-suggested automations / agents** (Salesforce Agentforce, Freddy, Creatio AI) — integration/later; park under Deferred.

## 5. Recommended build scope (this pass — 4 models)

All under `apps/sales/models/WorkflowProcessAutomation/` (PascalCase sub-module folder per backend package rule), templates under `templates/sales/workflow/…`. Bullets covered: **1 (designer), 2 (assignment), 3 (approvals), 4 (alerts) get a model each; bullet 5 (enrichment & cleansing) is deliberately NOT given a new model** — its auto-update half is already `PartyEnrichmentEvent` (8.3), and its duplicate-detection/merge half is deferred whole (§7) rather than half-built, because a merge is the most destructive write path in the module and the 4-model cap is spent on the four bullets that have zero sales-scoped tables today.

### Model 1: `SalesProcessDefinition` [SPD-] — bullet 1 (Visual Process Designer)
- **Justified by:** versioned trigger→steps definitions (Salesforce Flow versions, Zoho Blueprint publish lifecycle, Dynamics BPF stages, Creatio designer); re-enrollment caps (HubSpot); mandatory-data gating (Zoho/Dynamics).
- **Base:** `TenantNumbered`, `NUMBER_PREFIX = "SPD"` (verified unused).
- **Key fields:** `name`, `description`, `version` (PositiveInteger, default 1), `status` choices `draft/active/paused/archived`, `target_entity` choices `lead/opportunity/quote/order/case/contract/subscription` (targets are `crm.Lead`, `crm.Opportunity`, `sales.CPQQuote`, `scm.SalesOrder`, `crm.Case`, `sales.CustomerContract`, `sales.CustomerSubscription` — all verified), `trigger_event` choices `created/updated/stage_changed/field_value/date_reached/inactivity`, `trigger_field`, `trigger_value`, `conditions` JSONField (bounded validator cloned from `LeadRoutingRule.validate_routing_conditions`), `nodes` JSONField (ordered list of `{seq, type: approval|assign|notify|update_field|create_task|wait|branch, params}`; same bound rules: ≤20 nodes, ≤16 KiB, scalars only), `max_enrollments` (PositiveSmallInteger, default 1), `priority`, `is_active`, `owner` FK `settings.AUTH_USER_MODEL`, `job_definition` FK `core.JobDefinition` (SET_NULL, null — for time-based triggers; verified exists).
- **FKs:** `accounts.User`; optional `core.JobDefinition`; optional `core.WorkflowDefinition` registry row created at Integrate (single writer).

### Model 2: `SalesAssignmentRule` [SAR-] — bullet 2 (Auto-Assignment)
- **Justified by:** Salesforce assignment rules; LeanData/Q-Assign mode set (round robin, capacity, territory, fallback, SLA reassignment); Freshsales territory auto-assignment; HubSpot owner rotation; 8.1's Q12/Q13 hand-off (capacity-aware load balancing).
- **Base:** `TenantNumbered`, `NUMBER_PREFIX = "SAR"` (verified unused).
- **Key fields:** `name`, `target_entity` choices `lead/opportunity/case` (**lead routing DELEGATES to `sales.LeadRoutingRule`'s resolver per 8.1's ruling — SAR never re-decides a lead owner**), `match_mode` all/any, `conditions` JSONField (same validator), `is_catch_all`, `assignment_mode` choices `fixed_owner/round_robin/load_balanced/territory_manager/escalate_manager`, `default_owner` FK User, `eligible_owners` M2M User, `fallback_owner` FK User, `territory` FK `crm.Territory` (verified via LeadRoutingRule FK), `max_open_records` (capacity), `cursor` + `last_assigned_owner` + `last_assigned_at` (race-safe round-robin state, 8.1 pattern), `escalate_after_hours`, `escalate_to` FK User, `priority`, `is_active`.
- **FKs:** `accounts.User`, `crm.Territory`. Unique `(tenant, name)`.

### Model 3: `SalesApprovalDecision` [SAD-] — bullet 3 (Approval Workflows)
- **Justified by:** Salesforce multi-tier approval steps; Power Automate sequential chains; Zoho multi-level approvals; house pattern `procurement.RequisitionApproval` (immutable per-tier decision row, snapshotted `tier_count`, `unique_together (tenant, target, tier)`, written only inside the deciding view's atomic block, mirrored to `core.AuditLog`).
- **Base:** `TenantNumbered`, `NUMBER_PREFIX = "SAD"` (verified unused).
- **Key fields:** `approval_kind` choices `discount/credit/exception/contract`; target FKs (exactly one required, enforced in `clean()`): `quote` FK `sales.CPQQuote` PROTECT null, `order_hold` FK `sales.OrderHold` PROTECT null, `contract` FK `sales.CustomerContract` PROTECT null; `record_label` CharField (denormalized display, crm.ApprovalRequest pattern); `approval_rule` FK `sales.QuoteApprovalRule` SET_NULL null (the gate that fired); `tier` PositiveSmallInteger (1-based), `tier_count` PositiveSmallInteger (snapshot); `approver_role` FK `accounts.Role` SET_NULL null; `approver` FK User SET_NULL null; `decision` choices `approved/rejected`; `comment`; `requested_by` FK User; `requested_at`, `due_at` (DateTime, null — SLA display, `core.SlaRule` records the intent), `decided_at` (auto_now_add). `unique_together (tenant, approval_kind, quote/order_hold/contract, tier)` implemented as three partial UniqueConstraints or a computed `target_key` CharField (contract decision for the spec — procurement's `(tenant, requisition, tier)` precedent suggests a single `target_key` = `"<kind>:<pk>"` keeps it simple).
- **Pending state = absence of a decision row at the current tier** (procurement's "the register IS the history"); request status shown on the target (`CPQQuote.approval_status` already exists and is flipped by the deciding view).
- **FKs:** `sales.CPQQuote`, `sales.OrderHold`, `sales.CustomerContract`, `sales.QuoteApprovalRule`, `accounts.User`, `accounts.Role` — all verified.

### Model 4: `SalesAlertTrigger` [SAT-] — bullet 4 (Notification & Alert Engine)
- **Justified by:** HubSpot stage-change notifications; monday CRM conditional alerts; LeanData SLA alerts; Salesforce milestone alerts; 8.1's H8 hand-off (first-response SLA breach alerts); 8.16's `MobileDealAlert` types as the record-side delivery target.
- **Base:** `TenantNumbered`, `NUMBER_PREFIX = "SAT"` (verified unused).
- **Key fields:** `name`, `alert_type` choices `deal_inactivity/stage_change/milestone/approval_requested/sla_breach/contract_expiry/quota_attainment`; `target_entity` choices (same set as SPD); `conditions` JSONField (bounded validator); `inactivity_days` PositiveSmallInteger null; `severity` choices `low/normal/high/urgent` (mirror `MobileDealAlert.URGENCY_CHOICES`); `audience_kind` choices `role/user/owner/all` (mirror `core.NotificationRule.AUDIENCE_CHOICES`); `audience_role` FK `accounts.Role` null; `audience_users` M2M User; `notification_rule` FK `core.NotificationRule` SET_NULL null (platform delivery route — reuse, never re-invent channels); `cooldown_hours` PositiveSmallInteger default 24; `last_evaluated_at`, `last_fired_at`, `fire_count`; `is_active`, `priority`.
- **Delivery this pass = record rows only:** firing writes `sales.MobileDealAlert` (8.16, verified) for user-targeted alerts and/or emits the event key against `core.NotificationRule`; **no email/push socket code** (integration/later, matches 8.16 §7.3 and 8.18 ownership).
- **FKs:** `accounts.Role`, `accounts.User`, `core.NotificationRule`, `sales.MobileDealAlert` (write target, not FK) — all verified.

**Deferred within scope:** weighted/skill-based distribution modes (4.2), parallel approval branches + delegation (4.3), duplicate cluster/merge tables (4.5), `SalesProcessRun` execution-log table (4.6). Each goes to `.agents/tasks/gaps-sales-8.17.md` at close-out.
