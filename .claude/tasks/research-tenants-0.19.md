### Honesty discipline (house rule, from the 0.17/0.18 `LIVE_LINKS` comments)
NavERP has **no scheduled task runner** in `apps/` (0.20's "Job Scheduler" is unbuilt) and **no entitlement-enforcement middleware**. Anything phrased as "auto-renews", "notifies", "blocks", or "reclaims automatically" must ship as a **recorded state an operator drives** (a row, a status, a date, a verb that writes an evidence stamp), with page prose that says so. Declines are listed explicitly, not dressed up.
## Leaders surveyed (with source links)

1. **Microsoft 365 admin center** — per-user/per-group seat assignment & reclamation at the largest-scale admin console in the world; the reference model for "purchased vs assigned vs unassigned" · https://learn.microsoft.com/en-us/microsoft-365/admin/manage/assign-licenses-to-users?view=o365-worldwide
2. **Salesforce Editions & Pricing** — per-user license model, Flex Credits, add-on products, annual-prepay contract terms, trial-not-production rule · https://www.salesforce.com/editions-pricing/
3. **Chargebee — Entitlements / Feature Management / Subscription Entitlements** — the most explicit entitlement *override* semantics surveyed: feature lifecycle (draft→active→archived), plan-level vs subscription-level grants, `Forever` vs `Until <date>` time-boxed grants, an enable/disable toggle per grant, and an Activity Log of who changed what · https://www.chargebee.com/docs/2.0/entitlements.html · https://www.chargebee.com/docs/2.0/feature-management.html · https://www.chargebee.com/docs/2.0/subscription-entitlements.html
4. **Lago — Plans / Entitlements** — the cleanest separation of a *feature* from a *plan's privilege values on that feature*, with typed privileges (`boolean` / `integer` / `select`), per-subscription entitlement override for negotiated contracts, add-ons as fixed charges, and an explicit "plan properties lock once a plan is linked to an active subscription" rule · https://doc.getlago.com/guide/plans/overview · https://doc.getlago.com/guide/entitlements
5. **OpenMeter (Kong) — Entitlements & Limits / Product Catalog** — entitlement *types* (Metered / Static / Boolean), a `Grant` entity for one-time or recurring top-ups, and a catalog that versions plans so pricing changes roll out without disturbing existing subscriptions · https://openmeter.io/docs/guides/entitlements/overview · https://openmeter.io/docs/product-catalog/overview
6. **Stripe — Subscriptions lifecycle / thresholds / billing credits** — the authoritative statement of subscription *statuses* (`trialing`/`active`/`past_due`/`unpaid`/`canceled`/`incomplete`), **usage thresholds** that alert or invoice mid-period without waiting for the cycle end, and **credit grants** with an explicit state machine (`Pending`/`Granted`/`Depleted`/`Expired`/`Voided`) plus `effective_at`/`expires_at` · https://docs.stripe.com/billing/subscriptions/overview · https://docs.stripe.com/billing/subscriptions/usage-based/thresholds · https://docs.stripe.com/billing/subscriptions/usage-based/billing-credits
7. **Stripe — record usage with the API** — how consumption actually reaches a meter (meter events, idempotency keys, timestamp windows, dimension cardinality, error-report events), i.e. why a self-reported `UsageRecord` is a *different product* from a metered pipeline · https://docs.stripe.com/billing/subscriptions/usage-based/recording-usage-api
8. **Maxio (Zuora)** — seat-based / usage-based / **hybrid** pricing in one subscription, and the statement that entitlements are "features created with a type, access, usage limit, or service right, then built into your plans", with a plan upgrade automatically moving limits · https://www.maxio.com/product/subscription-management/

**Caveat on sourcing, stated honestly:** Zuora's own developer docs and Salesforce's Help pages are JS-rendered and returned no readable body to the fetcher. I cite Maxio for the Zuora-lineage model and the Salesforce pricing page (which did render) rather than claiming detail I could not read. Eight sourced pages, six distinct vendors.
## Feature catalog (this sub-module only)

### Bullet 1 — License Allocation & Seats (per-module/per-user assignment and reclamation)

- **Seat grant as a first-class row, not a counter** — one assignment record per (subscription, user, module) with a lifecycle status, so "reclaim" is a state change with an audit trail rather than a decrement. · seen in: Microsoft 365 (unassign from the Active users page; a removed license frees the seat immediately; a 30-day data hold follows) · priority: **table-stakes** · spine: **new table `LicenseAssignment`** FK→`accounts.User` (verified) + `tenants.Subscription` (verified) · **buildable now**
- **Purchased vs assigned vs unassigned seat count on one page** — the single most-asked admin number; derived, never stored. · seen in: Microsoft 365 (the Licenses page separates direct assignments from group-derived assignments and shows the unassigned pool) · priority: **table-stakes** · spine: derived property over the new table + `Subscription.seats` (verified) · **buildable now** (computed in the view off one grouped query — the `_usage_summary` precedent in `apps/tenants/views/UsageRecord.py` is the pattern to copy)
- **Per-module vs tenant-wide grant** — a seat can authorize the whole tenant or a single NavERP module. · seen in: Microsoft 365 (turn individual apps/services on or off within one assigned license) · priority: **common** · spine: `module_slug` char, matching `core.ModuleAccessScope.module_slug` (verified) — **NOT** a FK, because no module master exists · **buildable now**
- **Assignment source: direct vs group/rule-derived** — records *why* a seat is held, which is what makes a bulk reclaim safe. · seen in: Microsoft 365 (direct assignment vs group membership, displayed as distinct assignment kinds) · priority: **common** · spine: new table choice column · **buildable now**
- **Reclaim verb that writes an evidence stamp** — reclaim = set status + timestamp + reason, never a silent delete. · seen in: Microsoft 365 (deleting a user account returns the license to the pool immediately) · priority: **table-stakes** · spine: new table + `core.AuditLog` via the `write_audit_log` helper (verified in `apps/core/utils.py`) · **buildable now**
- **Per-seat effective window (`assigned_from` / `expires_on`)** — a seat granted for a term is not a seat granted forever. · seen in: Chargebee (`Forever` vs `Until <date>` on a subscription-level entitlement) · priority: **common** · spine: new table · **buildable now**
- **⚠️ DECLINE — automatic deprovisioning of the login.** This repo has no identity-provisioning integration; nothing here can suspend an `accounts.User` as a side effect of a reclaim. Ship the reclaim as a recorded status and say plainly in the page prose that the seat is released but the account is not disabled. A button labelled "deprovision" that only edits a status column would be exactly the dishonesty the `LIVE_LINKS` comments are written against.
- **Deferred — SCIM / group-sync.** Microsoft 365's group-based assignment implies a directory sync. No SCIM in this repo; a future pass may add an `accounts`-side sync register, but 0.19 should not pretend to have one.

### Bullet 2 — Plan & Entitlement Management (feature entitlements by plan tier, add-ons)

- **Plan tier as a char vocabulary, NOT a new `PlanTier` table** — the repo already ships `Tenant.PLAN_CHOICES` (free/starter/pro/enterprise) and `Subscription.PLAN_CHOICES` aliases it. A rate-card/catalog engine is Zuora-scale and is not this sub-module. · seen in: OpenMeter (a *versioned* catalog is the enterprise answer — deliberately not built here) · priority: **table-stakes** · spine: **reuse `core.Tenant.PLAN_CHOICES` (verified)** · **buildable now**
- **Feature catalog: one row per licensable capability, with a stable `key`** — the thing a plan grants. · seen in: Lago (a feature is a stable `code` + name, not necessarily directly billed), Chargebee (a feature with a type, id-slug, display name, entitlement units) · priority: **table-stakes** · spine: **new table `EntitlementFeature`** · **buildable now**
- **Typed privileges on a feature — boolean / integer / select** — the single most reusable idea in the survey. One feature can be *on/off* (`sso`), *capped* (`seats` → integer max), or *chosen from a list* (`sso_provider` → select); the `EntitlementFeature` row carries the vocabulary and the plan carries the value. · seen in: Lago (privilege `value_type` ∈ boolean / integer / select, set on the feature, valued on the plan), OpenMeter (entitlement types Metered / Static / Boolean) · priority: **differentiator** · spine: new table + choice columns · **buildable now**
- **Plan→feature grant with the privilege's value** — the "pro gets 50 seats" row. · seen in: Lago (features entitled to a plan, each privilege valued per plan), Maxio (features with a type / access / usage limit / service right built into plans) · priority: **table-stakes** · spine: new `PlanEntitlement` table · **buildable now**
- **Add-ons as first-class purchasable extensions** — a pack that grants features without a plan change. · seen in: Lago (fixed charges / add-ons attached to a plan), Chargebee (addons unlock features alongside plans and charges), OpenMeter (add-on as a self-service plan extension) · priority: **common** · spine: `is_add_on` boolean on the plan-entitlement table — recommend the **boolean on the same table** to stay inside the 1–4 model budget · **buildable now**
- **Subscription-level override of a plan grant** — the negotiated-contract case: this one customer gets 30 seats on Starter. Precedence is the whole point. · seen in: Chargebee (*"Entitlements assigned at the subscription level take precedence over entitlements assigned at the product catalog level"*), Lago (a per-subscription override creates an "overridden subscription") · priority: **differentiator** · spine: optional FK from the plan-entitlement row to `tenants.Subscription` (verified) + an `is_override` flag · **buildable now**
- **Time-boxed grant (`effective_from` / `effective_to`)** — a trial-scoped or campaign-scoped entitlement that lapses on its own. · seen in: Chargebee (`Forever` vs `Until <date>`) · priority: **common** · spine: date columns on the same table · **buildable now**
- **Archival, not deletion** — retiring a feature must not rewrite what past subscriptions were entitled to. · seen in: Chargebee (an archived feature's existing entitlements can only be removed, never edited; only draft/archived features are deletable) · priority: **common** · spine: `status` on the feature + freeze-on-referenced, the same discipline `UsageRecord.is_billed` already uses (verified) · **buildable now**
- **⚠️ DECLINE — price books, rate cards, tiered/volume/graduated unit pricing, multi-currency billing.** All surveyed and all out of scope: they are a monetization engine, not a sub-module, and `Tenant.PLAN_CHOICES` is the only price vocabulary this repo has. Chargebee's rate card and Stripe's graduated-tier volume math are parked wholesale.
- **Deferred — plan versioning / grandfathering.** OpenMeter's *Plan Version* + *Plan Phase* and Chargebee's *Grandfathering Entitlements* both exist so a price change can roll out without disturbing existing subscriptions. In NavERP a plan change is an explicit operator edit to `Subscription.plan`; versioning would add a catalog for its own sake. Park.
- **Boundary note — do NOT collide with `core.FeatureFlag`.** `FeatureFlag` (verified) already models `key` + `is_enabled` + `applies_to_plan` and is the *runtime* on/off switch. `EntitlementFeature` is the *commercial* catalog — what the plan sells. They are deliberately different: FeatureFlag is a toggle; EntitlementFeature carries typed privileges and grants. The plan page may *display* the related flags, and a code comment should say the two are not joined, because `FeatureFlag.applies_to_plan` is a free-text char with no FK and no integrity. Wiring them is a later pass at most.
### Bullet 3 — Usage Metering & Quotas (consumption tracking, overage alerts, fair-use limits)

- **Consumption rows per metric per period with DERIVED allowance and overage** — **already built** as `UsageRecord` (verified: `included_allowance`, `overage_quantity`, `is_overage` are properties, deliberately never stored, so a price-list change cannot rewrite what last month actually consumed). **0.19 does not rebuild this.** · priority: **table-stakes (done)** · spine: `tenants.UsageRecord` · **already built by 0.1**
- **A per-tenant QUOTA — the commercial ceiling — as its own row** — the missing half. `UsageRecord` measures; nothing declares the limit a tenant is entitled to consume. The surveyed vocabulary is "a quota is a number plus an action when crossed". · seen in: Stripe (usage thresholds `usage_gte` on a subscription item, monetary thresholds `amount_gte`, and `reset_billing_cycle_anchor` so hitting a threshold can re-anchor the cycle), Lago (`usage_thresholds` on a plan, `minimum_commitment`, progressive billing that invoices when cumulative usage reaches a threshold) · priority: **table-stakes** · spine: **new table `UsageQuota`** FK→`tenants.Subscription` + `metric` aligned to `UsageRecord.METRIC_CHOICES` (the verified vocabulary) · **buildable now**
- **Warning threshold as a percentage of the quota** — the "you're at 80%" alert, which is a *different number* from the limit. · seen in: Stripe (thresholds exist to alert before overage is invoiced) · priority: **table-stakes** · spine: new table · **buildable now**
- **Fair-use / overage policy vocabulary on the quota** — alert-only vs bill-the-overage vs hard-stop. Naming the policy is honest; *executing* a hard stop is not (see the declines). · seen in: Lago (the allowance-vs-quota distinction — an allowance is included usage, a quota is the maximum that may trigger overage *or access restriction*; the vocabulary is Lago's) · priority: **differentiator** · spine: new table choice column · **buildable now**
- **Quota-vs-consumption board (the overage alert surface)** — one row per metric: consumed, included, overage, % of quota, and whether the warning line has been crossed. This is the page the bullet actually names. · seen in: all metering vendors · priority: **table-stakes** · spine: computed view over `UsageRecord` + `UsageQuota`, mirroring the verified `_usage_summary()` pattern · **buildable now**
- **Crossed-threshold state with a timestamp** — "this quota was breached on the 14th", recorded once. · seen in: Stripe (a threshold is a *fact* that fired, not a live calculation) · priority: **common** · spine: `breached_at` on the quota, written only by a verb · **buildable now** — and per the agreed L36 boundary this records the *commercial* breach only; the 0.18 abuse-bound evidence stays in `SecurityThreat`
- **⚠️ DECLINE — automatic throttling / hard-stop on quota breach.** There is no request-path interceptor in this repo that reads a quota and refuses an operation. `UsageQuota.action_on_breach` is a **recorded policy**, and the page must say the system does not enforce it. Shipping an "enforcement" toggle that enforces nothing is precisely the dishonesty this repo's `LIVE_LINKS` comments are written against.
- **⚠️ DECLINE — metered event ingestion.** Stripe's meter-event API (idempotency keys, 35-day event window, dimension cardinality, error-report events) is a live pipeline. NavERP's `UsageRecord` is **hand-entered consumption evidence**. That is an honest, useful product; it is not a meter. Do not describe the usage page as "live metering".
- **Deferred — prepaid credits / committed-use grants.** Stripe's *credit grants* (`Pending`/`Granted`/`Depleted`/`Expired`/`Voided` with `effective_at`/`expires_at`) and OpenMeter's *Grant* entity are real and would make a good 0.19 follow-up, but a credit balance is money and a second money store would brush against L29. Park.

### Bullet 4 — Billing & Invoicing Integration (subscription billing, proration, gateway sync)

- **Subscription record with plan, cycle, amount, seat count, gateway ids, renewal date** — **already built** as `tenants.Subscription` (verified). · priority: **table-stakes (done)**
- **Subscription invoice with an auto-minted number and a gateway id** — **already built** as `tenants.SubscriptionInvoice` (verified: `SINV-#####` minted in `save()`, `unique_together ("tenant","number")`, indexed `stripe_invoice_id`). · priority: **table-stakes (done)**
- **Payment-gateway sync with signature verification and idempotency** — **already built** as `stripe_webhook` (verified: `stripe.Webhook.construct_event` with the security WARNING comments, `client_reference_id` matching, `invoice.paid` de-duplicated on `stripe_invoice_id`). Also `subscription_checkout` + `subscription_mark_paid` for the unconfigured-Stripe fallback. · priority: **table-stakes (done)**
- **Usage→invoice roll-up with a frozen billed stamp** — **already built**: `usagerecord_mark_billed` refuses to mark without a linked invoice and refuses to edit a billed row (verified). · priority: **table-stakes (done)**
- **Invoice ↔ subscription lifecycle status coherence** — the `past_due` / `unpaid` / `canceled` vocabulary already matches Stripe's own status set (verified: `Subscription.STATUS_CHOICES` = trialing/active/past_due/canceled/incomplete). **Nothing to add**; the webhook already writes these. · priority: **common (done)**
- **⚠️ DECLINE — proration.** Every vendor surveyed implements mid-cycle plan-change proration (Stripe proration, Zuora amendments, Lago `prorated: true` per charge, Chargebee mid-term changes). NavERP has no proration engine and, more importantly, **no arithmetic source of truth for what a partial period is worth** — that would be a second financial calculation beside the GL (L29). `Subscription` can be edited; the honest 0.19 move is to leave the edit visible and **not** compute a credit. Record the reason in the contract, and if proration is ever built it belongs to whoever owns the money.
- **Boundary — 0.19 does not touch the accounting GL.** `accounting` owns the financial ledger (L29); `SubscriptionInvoice` is a *gateway-facing* document, deliberately separate. No `JournalEntry` may be minted from a subscription invoice in this pass.
### Bullet 5 — Renewal & Expiry Management (auto-renewals, grace periods, expiry notifications)

- **Renewal date + days-remaining on the subscription** — **already built**: `Subscription.renews_on` and `days_left()` (verified). · priority: **table-stakes (done)**
- **Trial state distinct from active** — **already built** (`trialing` is in `STATUS_CHOICES`; the webhook moves `incomplete`→`active` on payment). · priority: **table-stakes (done)**
- **Auto-renew flag as a recorded commitment** — Stripe's `cancel_at_period_end` inverted: a boolean on the subscription saying "renews unless someone turns this off". · seen in: Stripe (cancel at period end vs cancel now), Salesforce (auto-renew subscriptions at contract end) · priority: **table-stakes** · spine: **field addition to `Subscription`** (verified, one column) + a board that computes "renews in N days, auto-renew off" · **buildable now**
- **Grace period as an explicit, dated state — never silent** — the vendor-corroborated rule is that a lapse is a *recorded transition with a date*, not a hidden flag flip. · seen in: Microsoft 365 (removing a license holds the data for a **30-day grace period** before deletion — the grace window is a *stated, dated* thing), Stripe (`past_due`/`unpaid` are distinct from `canceled`) · priority: **differentiator** · spine: `grace_ends_on` on `Subscription` + a `status` value the board reads · **buildable now**
- **Renewal/expiry board — one page listing every subscription by days-to-renewal with its grace state** — the artifact the bullet actually names. · seen in: all six vendors (the renewal calendar is the admin's home screen) · priority: **table-stakes** · spine: computed over `Subscription` (verified) · **buildable now**
- **Notification policy for "your plan expires in N days"** — reuse the existing notification spine, do not build a subscriber table. · seen in: Chargebee (expiry and grandfathering are notification-worthy events) · priority: **common** · spine: **reuse `core.NotificationRule` / `NotificationTemplate` / `NotificationChannel` (verified)** — the 0.19 page links to and configures these; `tenants` adds no channel, template or preference model · **buildable now**
- **⚠️ DECLINE — the automatic renewal *action*.** "Auto-renewals" in the bullet cannot be *executed*: there is no scheduler in `apps/` (0.20's Job Scheduler is unbuilt) and no stored mandate to charge. Ship `auto_renew = True` as a **recorded intent** and state on the page that renewal is actioned by the billing process, not by this page. A toggle that silently does nothing is the exact failure the 0.17/0.18 comments warn against.
- **⚠️ DECLINE — sending the expiry email.** `send_mail` exists elsewhere in the repo (verified in `apps/core/views.py`, `apps/core/views/_helpers.py`, and `apps/hrm/.../Interview.py`) but **no `tenants` code sends mail and no `NotificationRule` has a dispatcher**. ## Recommended build scope (this pass — 4 models)

> Scope: **4 new models in `apps/tenants`**, plus **field additions to the existing `Subscription`**. Bullets 3 and 4 are largely already satisfied by 0.1's `UsageRecord` / `SubscriptionInvoice` / webhook — the research says so plainly rather than inventing work. All entity files stay **FLAT** at the package root (foundation app, no sub-module level) and templates at `templates/tenants/<entity>/{list,detail,form}.html` (verified: that is the existing shape, e.g. `templates/tenants/subscription/`, `templates/tenants/usagerecord/`).

- **`EntitlementFeature`** [`ENT-`] — the feature catalog. Fields justified by: *typed privileges* (Lago boolean/integer/select, OpenMeter Metered/Static/Boolean) → `code`, `name`, `description`, `privilege_type`, `select_options`, `status` (draft/active/archived — Chargebee's lifecycle), `is_add_on`, `is_active`, `notes`, `created_at`. **FKs:** `tenant` → `core.Tenant` (verified). Deliberately **not** FK'd to `core.FeatureFlag` (see the bullet-2 boundary note). Prefix `ENT-` probed clear of every `next_number()` prefix in the repo.
- **`PlanEntitlement`** [`PE-`] — the grant: plan tier × feature × privilege value, with the override and the time-box. Fields justified by: *plan→feature grant with a value* (Lago), *add-ons* (Lago fixed charges / Chargebee addons / OpenMeter add-on) → `is_add_on`, *subscription-level override precedence* (Chargebee, Lago) → nullable `subscription` FK + `is_override`, *`Forever` vs `Until <date>`* (Chargebee) → `effective_from` / `effective_to`, `privilege_value` (char, holding `true` / `10` / `okta`), `is_enabled`, `notes`. **FKs:** `tenant` → `core.Tenant` (verified), `feature` → `tenants.EntitlementFeature`, `subscription` → `tenants.Subscription` (verified, `SET_NULL`). `unique_together` = (`tenant`, `plan`, `feature`, `subscription`) so a plan-level grant and an override coexist without collision.
- **`UsageQuota`** [`UQ-`] — the commercial ceiling per metric. Fields justified by: *Stripe usage/monetary thresholds*, *Lago `minimum_commitment` + `usage_thresholds`*, *Lago's allowance-vs-quota distinction* → `subscription` FK, `metric` (aligned to `UsageRecord.METRIC_CHOICES`, the verified vocabulary), `quota_limit`, `warn_at_pct`, `action_on_breach` (alert/charge/block — **recorded policy, not enforced**), `is_fair_use`, `breached_at` (nullable, written only by a verb — the `UsageRecord.is_billed` evidence-stamp precedent), `period` (monthly/yearly), `notes`. **FKs:** `tenant` (verified), `subscription` → `tenants.Subscription` (verified). Cross-page consistency with `UsageRecord.subscription` matters: the board must join on the same subscription.
- **`LicenseAssignment`** [`LIC-`] — the seat register. Fields justified by: *Microsoft 365 assign/unassign/reclaim + purchased-vs-assigned*, *Chargebee `Forever` vs `Until`*, *group-derived vs direct* → `user` FK → `accounts.User` (verified; `User.tenant` is **nullable**, so a null-tenant superuser must be filtered out of seat counts), `module_slug` (char, matching `core.ModuleAccessScope.module_slug` — **not** a FK, since no module master exists; blank = tenant-wide), `status` (active/reclaimed/revoked/expired), `assignment_source` (direct/group/rule), `assigned_from`, `expires_on`, `reclaimed_on`, `reclaim_reason`, `notes`. **FKs:** `tenant`, `user` → `accounts.User`, `subscription` → `tenants.Subscription` (verified). Derived `is_reclaimable` / seat-count helpers stay **properties**, never columns.

**Plus, on the existing `Subscription` (field additions only, no new model):** `auto_renew` (Boolean, default True) and `grace_ends_on` (DateField, null) — bullet 5's auto-renew intent and grace window, both *recorded*, plus the computed renewal board. This is deliberately a column pair rather than a 5th model: a renewal commitment is a property of the subscription, and inventing a table for two fields would be over-modelling.

**Derived (no model), following the 0.17/0.18 board precedent:** the **quota-vs-consumption board** (metric, consumed, included, overage, % of quota, warning crossed) and the **renewal & expiry board** (subscription, plan, days to renewal, auto-renew, grace state) — both computed in the view off one grouped query, following the verified `_usage_summary()` pattern in `apps/tenants/views/UsageRecord.py`.

### Not built, and the reason — carry these into the `LIVE_LINKS` comment verbatim
`entitlement enforcement` (no interceptor) · `seat auto-deprovision` (no identity sync) · `proration` (no money arithmetic; L29) · `metered usage ingestion` (no event pipeline) · `prepaid credit grants` (second money store; L29) · `rate cards / tiered pricing / multi-currency billing` (monetization engine, not a sub-module) · `plan versioning & grandfathering` (a catalog for its own sake) · `automatic renewal execution` (no scheduler — 0.20) · `expiry email delivery` (no sender in `tenants` — 0.20/0.21). Each must read as a *recorded state* or a *link to the owning sub-module*, never as a capability.

## Belongs to sibling sub-modules (parked, not scoped here)
- **Alert thresholds, capacity/scaling triggers, health monitoring** → **0.17** (already built: `core.AlertRule` / `AlertEvent` / `ServiceComponent`). Its own `LIVE_LINKS` comment already ceded *"quota management is the billing sub-module's; 0.17 keeps only the scaling trigger"* — 0.19 is that billing sub-module.
- **Abuse bounds, rate limiting, WAF, breach evidence** → **0.18** (already built: `core.IpAccessRule`, `SecurityThreat`). A quota is the *commercial* ceiling; 0.18's rate limit is the *abuse* bound. `UsageQuota` must never be presented as an anti-abuse control.
- **Tenant suspension / read-only lockout on expiry** → **0.20** Admin Console & System Operations (the enforcement action on a lapsed subscription).
- **Scheduled renewal runs, the notification dispatcher, bulk job management** → **0.20**.
- **Contract terms, audit attestation of licence counts, regulatory retention of billing records** → **0.21** Compliance, Governance & Risk.
- **Multi-currency billing and FX for invoices** → **0.15** Localization (which already owns exchange-rate concerns); 0.19 bills in a single currency.
- **The financial GL / journal entries for subscription revenue** → **`accounting`** (L29). No `JournalEntry` from 0.19.

## Deferred (later passes / integrations)
- **Entitlement enforcement at request time** — a middleware or decorator reading `PlanEntitlement` to gate a view. Real and valuable, but it changes runtime behaviour across every module and deserves its own pass with its own review, not a rider on a CRUD sub-module.
- **Prepaid credit / committed-use grants** (`CreditGrant`-style with `effective_at`/`expires_at`, OpenMeter `Grant`) — a later 0.19 follow-up, subject to the L29 money-ownership ruling.
- **SCIM / directory-sync seat provisioning** — Microsoft 365's group-based model implies it; no SCIM exists here.
- **Multi-gateway abstraction** — `stripe_utils` is Stripe-specific and degrades gracefully. A second gateway (and a `PaymentGateway` connector table) is integration work, and `core.ConnectorDefinition` (verified to exist) is the right future home.
- **Seat over-allocation warnings and reconciliation against a real order form** — the numbers are computable now; reconciling them against a contract is a 0.21 concern.
- **Price-book / rate-card / tiered-unit pricing** — parked wholesale; a monetization engine, not a sub-module.
