### 0.1 The `RateLimitPolicy` ruling — extend by FK, never re-declare

`core.RateLimitPolicy` is a **configuration row**: a number, a window, a scope. It is the closest thing in the repo to bullet 4's "rate limiting", it was built by 0.13, and its own docstring says in bold that **nothing enforces it**.

Three options were considered; two are rejected outright.

- **(REJECTED) Declare `core.SecurityRateLimit` / `AbuseThrottle`.** A second table with the same columns in a different app file is the exact parallel-schema bug **L29** forbids — and 0.17's own `Monitoring.py` docstring already names `core.RateLimitPolicy` as *"0.18's"*, i.e. 0.17 pointed at it rather than copying it. After 0.18 there would be two ways to say "1000 per hour" and nothing would say which is authoritative.
- **(REJECTED) Do nothing and point the sidebar at `core:ratelimit_list`.** Honest, but it leaves bullets 1 and 4 with **no new surface at all** and — more seriously — it leaves 0.18 with *no answer to "the limit was exceeded"*. A limit that has never been observed crossing is a number on a page: the 0.16 "reports success while nothing happened" failure.
- **(ADOPTED) 0.18 adds the observation / enforcement layer on top, FK'd to the policy.** The split is the one every real product makes and the one 0.17 already made with `AlertRule` / `AlertEvent` (**rule = configuration, event = occurrence**):

  | Concern | Owner | NavERP model |
  |---|---|---|
  | The limit itself (number, window, scope) | 0.13 | `core.RateLimitPolicy` — **unchanged, not edited, not forked** |
  | That the limit was **crossed**, by whom, from where | 0.18 | `SecurityThreat` with a `rate_limit_policy` FK (`SET_NULL`, `related_name="security_threats"`) |
  | The **IP that must not come back** | 0.18 | `IpAccessRule` with `direction="deny"` and an optional `rate_limit_policy` FK |
  | The alert that fires | 0.17 | `core.AlertEvent` via `SecurityThreat.alert_event` |

  Because the FK is by **string** (`"core.RateLimitPolicy"`), 0.18 needs no migration to `Integration.py`, no re-export edit to that file, and no change to 0.13's model — the L29 "later module EXTENDS by FK" shape exactly. The `WINDOW_CHOICES` vocabulary is **not** copied: neither 0.18 model needs a window, because the window lives on the policy they point at.

  **The docstring obligation (L38 / L52).** `SecurityThreat`'s docstring and every page built on it must say, in the same voice `RateLimitPolicy` already uses: *a row here is a report that a limit was crossed.* No middleware counts requests, no token bucket is consumed, no `429` is ever returned by NavERP code. If the build wires anything that *does* count, the prose is updated **in the same commit** — the reverse is the defect.

### 0.2 The 0.17-seam ruling — one enum value, no columns, no engine

`AlertRule.CATEGORY_CHOICES` already carries `("security", "Security")`, and a **committed test** (`test_monitoring_models.py:53`) asserts the value exists, with the docstring *"0.18 (Threat Protection) grows through exactly this one value, with no extra columns."* That is a contract and it binds this build. Three consequences:

1. **No new columns on any 0.17 model.** In particular: no `threat_level`, no `ip_address`, no `cvss_score`, no `mitre_technique` on `AlertRule`, `AlertEvent`, `Incident` or `ServiceComponent`. Those are **0.18 fields on 0.18 models**, and a 0.18 model that wants correlation FKs `AlertRule` / `ServiceComponent` / `AlertEvent` rather than widening them. (This is 0.17's research §4.1, verbatim, and it still stands.)
2. **No second alert / incident engine.** Bullet 5 ("Real-time security alerts and SIEM/SOC integration") is served by **writing into the tables 0.17 built**: a `SecurityThreat` row carrying an `alert_event` FK shows up in `core:firing_board`; an `AlertRule(category="security")` row shows up in `core:alert_rule_list`. There is no `SecurityAlert` table, no duplicate incident lifecycle, and no second board.
3. **The one place 0.18 *does* add a model is where 0.17 has no row at all.** `AlertEvent` has no `mitre_technique` and no source address; a *security* finding needs both, and `Monitoring.py` explicitly refuses to grow them. That is the whole justification for `SecurityThreat` existing rather than "just reuse `AlertEvent`".

**What 0.18 must NOT do to `Incident`:** add a `breach` incident type, a `regulatory_deadline` or a `forensic_log` column. Those are `SecurityIncident` fields. `SecurityIncident.incident` FKs `core.Incident` so the comms artifact and the security record stay one incident with two faces.

### 0.3 What 0.18 legitimately builds, given the repo has no detector

Verified absent from this repository (grepped, L28): there is **no** IDS/IPS agent, no packet capture, no log shipper, no log-collector in `config/settings.py`, no SIEM client, no WAF, no CAPTCHA library (`requirements.txt` is Django, PyMySQL, python-dotenv, stripe, Pillow, cryptography, pdfplumber, pytest, python-barcode, qrcode — nothing else), no scanner, no CI, and no scheduler. The only runtime middleware is `TenantMiddleware` and `SessionTimeoutMiddleware` (`apps/core/middleware.py`).

That does **not** mean 0.18 declines. It means 0.18 is a **register of declared findings** — exactly the posture 0.16 took for backups and 0.17 took for firings: a table of claims a person wrote, whose pages say so. A register is a legitimate ERP artifact; an auditor asks for the register, not for the IDS. A *pipeline* is not, and §3 declines those explicitly.

## 2. Recommended build scope — 4 models

All four go in **one new flat file**: `apps/core/models/Security.py` (Module 0 has no sub-module level — backend rule 9, exactly as `Monitoring.py` sits flat at the package root). Matching `apps/core/forms/Security.py` and `apps/core/views/Security.py`; templates flat at `templates/core/<entity>/{list,detail,form}.html`; URLs via the existing 37-line `crud(slug, name)` factory in `apps/core/urls.py` plus a handful of named board / action routes.

**Why four and not more.** Bullets 1-5 collapse onto four distinct nouns once the 0.17 seam and the `RateLimitPolicy` ruling are applied:

| NavERP noun | Bullets it carries | What it cannot absorb |
|---|---|---|
| a **threat** that was found | 1, 4, 5 | cannot be a policy — a finding is an occurrence |
| an **address that is allowed or denied** | 1, 4 | cannot be a finding — it is a standing configuration |
| a **known weakness** in a component or dependency | 2 | cannot be a threat — no adversary observed it |
| a **security incident** with a notification clock | 3 | cannot be a threat — it is the response, not the finding |

A fifth ("asset / attack-surface inventory") would be the **only** way to make attack-path, exposure and WAF-target rows honest, and that is a department, not a field. Two further candidates were cut on purpose: an **evidence / artifact table** (§3 — a chain-of-custody table with no acquirer is the exact `DisposalRecord` fiction 0.16 refused) and a **notification / rule table** (0.12 owns it). **Fewer well-chosen models beats a sprawl**; 0.17 shipped four and the shape transfers exactly.

### 1. `SecurityThreat` — *a threat, as a declared finding*

- **Serves:** bullets 1 (anomaly / brute force), 4 (rate-limit breach, bot / abuse) and 5 (the correlated alert). This is the sub-module's centre of gravity.
- **Why it exists:** every product in §1 keeps a *notable / detection* record distinct from the rule that would have caught it and distinct from the incident that follows. NavERP has the rule half (`core.AlertRule`) and the incident half (`core.Incident`), and `AlertEvent` is explicitly built around a *threshold crossing with an observed value* — it has nowhere to put `T1110.001` or a source IP, and `Monitoring.py` refuses to grow columns. A security finding is therefore the one row 0.18 must add.
- **Key fields:** tenant; **`alert_event`** (FK `core.AlertEvent`, `SET_NULL`, `related_name="+"` — the 0.17 seam, §0.2); **`rate_limit_policy`** (FK `core.RateLimitPolicy`, `SET_NULL`, `related_name="security_threats"` — the rate-limit seam, §0.1); `service` (FK `core.ServiceComponent`, `SET_NULL`) + a `service_label` snapshot so the row still reads after the component is retired; `target_user` (FK `AUTH_USER_MODEL`, `SET_NULL`, `related_name="+"` — matches `DisposalRecord.performed_by`'s shape) and `target_credential` (FK `core.ApiCredential`, `SET_NULL`), so the finding says *who or what was targeted*; `title`; **`threat_type`** (`brute_force`, `credential_stuffing`, `anomalous_login`, `privilege_escalation`, `suspicious_api_activity`, `data_exfiltration`, `malware`, `phishing`, `waf_rule_match`, `rate_limit_exceeded`, `bot_abuse`, `other` — a **union** enum so one list renders all of bullets 1, 4 and 5); `severity` (**`AlertRule.SEVERITY_CHOICES` reused by reference**, not a fourth severity list — a finding correlated to a firing must sort with it); **`mitre_technique`** (free-text `CharField`, e.g. `T1110.001` — **a label, not a taxonomy table**; MITRE publishes a vocabulary that changes on its own release cycle, so freezing it into `CHOICES` here would go stale, and a `Technique` model would be a second copy of a public standard); `mitre_tactic` (free text, same reasoning); `source_ip` (**`GenericIPAddressField`**, nullable — the same field type as `accounts.LoginAttempt.ip`, so a finding and its evidence agree); `detected_at`; `occurrence_count`; `summary` / `detail`; **`evidence`** (free text, the **same field shape** as `BackupJob.evidence` and `DisposalRecord.evidence` — a ticket id, a log line somebody pasted, a screenshot path; **not** a payload, a stack trace or a captured packet, because NavERP collects none); `status` (`new` / `triaged` / `investigating` / `contained` / `resolved` / `false_positive` / `ignored` — Defender for Cloud Apps' acknowledge / resolve / suppress / dismiss shape, mapped to a lifecycle NavERP can actually hold); `mitigated_by` (nullable FK to the `IpAccessRule` put in place — closing the loop between bullet 1's deny list and bullet 1's finding); `resolved_at` / `resolved_by`; `notes`; created_at. Indexes: `(tenant, -detected_at)`, `(tenant, status)`, `(tenant, threat_type)`, `(tenant, source_ip)`.
- **NULL is not 0, here too:** `source_ip` `NULL` means *"not from a single address"* (a dependency finding, a configuration finding) and must render `"—"`; a `source_ip` of `0.0.0.0` is a different and usually false claim.
- **Relates to:** FK `tenant`, `alert_event`, `rate_limit_policy`, `service`, `target_user`, `target_credential`, `mitigated_by`. **No FK to `AuditLog`, `BusinessRule`, `LoginAttempt` or `Incident`** — the first two are a different subject, and the last two are *read* by the boards rather than joined, because a join would imply NavERP correlates them and nothing does.

### 2. `IpAccessRule` — *an address that is allowed, or is not*

- **Serves:** bullet 1 (IP allow / deny lists — verbatim) and bullet 4 (the mitigation action taken against one).
- **Why it exists:** bullet 1 names IP allow/deny lists outright and **nothing in the repository has one** — grep-verified (L28), there is no IP list, no blocklist and no allowlist anywhere in `core`, `accounts` or `tenants`. It is also the natural landing place for a deny decision taken after a `SecurityThreat`, which is what closes bullet 1's loop.
- **Key fields:** tenant; `cidr` (**the IP address or CIDR block**, `CharField` with a validator — not a `GenericIPAddressField`, because a single-address field cannot hold `203.0.113.0/24` and CIDR is the normal unit of a deny list); `direction` (`allow` / `deny` — Cloudflare's `Allow` / `Block` pair; the two lists are one table because the *decision* is what differs, not the shape); `action` (`allow` / `block` / `challenge` / `managed_challenge` / `non_interactive_challenge` / `interactive_challenge` / `log` — **Cloudflare IP Access rule actions, verbatim**; `log` is the honest default, because a rule that claims to block when nothing blocks is the exact defect L52 exists to prevent); `service` (FK `core.ServiceComponent`, `SET_NULL` — which surface this protects, nullable for a workspace-wide rule); `rate_limit_policy` (FK `core.RateLimitPolicy`, `SET_NULL` — "this address was throttled under this policy", the §0.1 seam from the other side); `scope` (`workspace` / `service` / `credential` — mirrors `RateLimitPolicy.credential`'s own nullable scoping, so the two read consistently); **`reason`** (free text, required — *why this address is denied*; a deny entry with no reason is an unexplainable block); `source` (`manual` / `threat` / `rate_limit` / `import` — whether a person or a recorded finding put it here, and **nothing in NavERP chooses it automatically**); **`expires_at`** (nullable — a temporary block is the common case; `NULL` means permanent and must render `"permanent"`, never today's date); `is_active`; `added_by` (FK `AUTH_USER_MODEL`, `SET_NULL`) + `added_by_label`; `notes`; created_at / updated_at. `unique_together = (tenant, cidr, direction)` — the same address may legitimately be on both lists (a `/32` allow inside a `/24` deny is a real configuration), but not twice on the same side.
- **The honest-claim surface is the whole point of this model.** NavERP has no gateway, no proxy and no WAF in front of it, so **a row here is a written policy that some other layer would have to enforce.** The docstring and every page must say so in the same voice `RateLimitPolicy` already uses, and `action="block"` must render as *"would block"* wherever the page is describing NavERP rather than describing the policy.
- **Relates to:** FK `tenant`, `service`, `rate_limit_policy`, `added_by`. **No FK to `SecurityThreat`** — the causal link is recorded on the threat's own `mitigated_by`, so a threat can point at the rule that answered it without the rule having to know it existed.

### 3. `VulnerabilityFinding` — *a known weakness, and what was done about it*

- **Serves:** bullet 2 in full — scanning, dependency checks, patch scheduling.
- **Why it exists:** bullets 1/4 record what an adversary did; bullet 2 records what is **knowably wrong before anyone does anything**. Tenable, Qualys, Snyk, Dependabot and Wiz all keep this as a separate object from the alert stream for exactly that reason, and this repository has no model of it.
- **Key fields:** tenant; `title`; **`advisory_id`** (`CVE-…` / `GHSA-…` / vendor advisory, indexed — "have we seen this before" is the question a register exists to answer); **`finding_source`** (`dependency` / `operating_system` / `application` / `configuration` / `third_party` / `misconfiguration` — the scan class; this is what lets a `requirements.txt` line sit in the same list as an OS CVE without pretending they are the same kind of thing); `component` (FK `core.ServiceComponent`, `SET_NULL` — nullable, because a vulnerable *dependency* has no service); `package_name` + `installed_version` (blank for a non-dependency finding — the Snyk / Dependabot pair); **`severity`** (a **CVSS band** enum here and *only* here: `none` / `low` / `medium` / `high` / `critical`, Tenable's `severity` 0-10 bucketed; deliberately **different** from `AlertRule.SEVERITY_CHOICES`, because a CVSS band and a firing severity are different facts — the same reason `AlertRule.metric_key` overlaps `HealthMetric.METRIC_CHOICES` by string without meaning the same thing, and the file docstring must repeat that warning so the next agent does not "fix" it); **`cvss_score`** (nullable Decimal — `NULL` = *"not scored"*, rendered `"—"`, never `0`; a 0.0 CVSS is a real score and a different statement); `epss_score` (nullable, same discipline); **`fix_available`** (`yes` / `no` / `partial` — Snyk's `fixAvailable` made explicit, because "no fix exists" and "we have not fixed it" must never render as the same word); `fixed_in_version` (blank when there is no fix — the Snyk `fixedIn` / Dependabot *"no fix available"* pair); `status` (`open` / `in_progress` / `fixed` / `risk_accepted` / `false_positive` / `not_applicable` — Snyk's open / ignored / fixed plus Tenable's **exclusions** and Wiz's risk-acceptance, where each terminal value is a *decision somebody made*, not an absence of data); **`accepted_reason`** + `accepted_by` + `accepted_at` (required when `status="risk_accepted"` — an accepted risk with no stated reason is an unowned risk; this is the Tenable-exception discipline and it belongs on the finding, **not** in a separate exclusions table); **`due_on`** (nullable date — the patch schedule; `NULL` = *"no remediation deadline has been set"*, which is a different statement from today and must never be defaulted to it); `first_seen_at` / `last_seen_at` (Tenable's `first_seen` / `last_seen` pair — a finding still being seen is a different finding from one that has not recurred in 90 days); `remediation_note`; `evidence` (same free-text shape as everywhere else); `notes`; created_at / updated_at. Indexes: `(tenant, status)`, `(tenant, severity)`, `(tenant, advisory_id)`, `(tenant, -first_seen_at)`.
- **`due_on` derivation is 0.18 to argue, not to assume.** A severity-to-SLA mapping is a **policy** somebody writes down; a good shape is a nullable `due_on` on the finding plus an `sla_days`-by-severity constant held in `Security.py` and surfaced on the board, with the docstring saying plainly that **no scheduler reads it** (the `SyncSchedule.frequency` / `AlertRule.frequency` / `BackupJob.frequency` precedent — all three already say this in their own docstrings). 0.20 owns the scheduler.
- **Relates to:** FK `tenant`, `component`, `accepted_by`. **No FK to `ServiceComponent.current_status` or to `AlertEvent`** — a CVE is not a firing; if an operator wants one, they create the `AlertRule(category="security")` and the `AlertEvent` themselves, which is the 0.17 seam working as designed.

### 4. `SecurityIncident` — *the response, with a clock on it*

- **Serves:** bullet 3 in full — incident workflows, breach notification, forensic logging (narrative).
- **Why it exists:** 0.17's `Incident` is a **service-availability communications artifact** (public note vs internal note, impact, progress) and 0.17's research said so explicitly: 0.18 "must not expect 0.17 to have modelled breach notification, forensic evidence or regulatory timelines. Those are 0.18's fields." This is that model. It is also the only place in NavERP where a **regulatory clock** exists, and a clock with a derived deadline is the single most valuable thing an auditor or a DPO can be handed.
- **Key fields:** tenant; **`incident`** (FK `core.Incident`, `SET_NULL`, `related_name="security_incidents"` — the 0.17 seam; a breach is also an availability event, and this keeps one incident with two faces rather than two incidents); **`primary_threat`** (FK `core.SecurityThreat`, `SET_NULL`, `related_name="security_incidents"`); `title`; **`incident_class`** (`security_incident` / `data_breach` / `unauthorized_access` / `malware` / `phishing` / `insider_threat` / `policy_violation` / `denial_of_service` / `other` — the **union** enum, because `data_breach` is the one value that switches the whole notification block on); **`status`** (the NIST SP 800-61r2 lifecycle as a state machine: `detected` / `triage` / `investigating` / `contained` / `eradicated` / `recovered` / `closed` / `false_positive` — deliberately **not** 0.17's `Incident.status` union, because a breach does not pass through `scheduled` or `monitoring` and forcing it into that enum would be the L36 bug in the other direction); `severity` (again `AlertRule.SEVERITY_CHOICES` by reference); **`discovered_at`** (when the organisation became aware — the anchor for every legal clock, and the field the 72 hours run from); `contained_at` / `eradicated_at` / `recovered_at` / `closed_at` (nullable, system-set, off the form — L22); **`regulatory_deadline`** (**derived in `save()`** as `discovered_at + 72h` per GDPR Art. 33(1), `editable=False`, and a property rather than a stored column so the anchor and the deadline cannot drift); **`is_notifiable`** (nullable Boolean — `NULL` = *"nobody has decided yet"*, which is a third and very common state, and is exactly the situation the 72-hour clock exists to pressure); `notifiable_reason`; `authority_notified_at` (nullable, system-set) + `authority_reference` (the filing reference); **`subjects_notified`** (nullable Boolean) + `subjects_notified_at`; **`subject_exemption`** (`none` / `technical_measures` / `subsequent_measures` / `disproportionate_effort` — GDPR Art. 34(3)'s three exemptions, named as they are named in the Article, because the exemption is the defensible part of the record and an auditor asks for it first); `data_subjects_affected` and `records_affected` (both **nullable** PositiveInteger — Art. 33(3)(a) requires *approximate numbers*, and an unknown count is not a zero count); `dpo_contact` (Art. 33(3)(b)); `likely_consequences` (Art. 33(3)(c)); `measures_taken` / `measures_proposed` (Art. 33(3)(d)); **`forensic_log`** (a long text field — the *narrative*: what was found, what was preserved, what remains to be collected, in what order, by whom; **not** a log pipeline, see §3); `root_cause`; `lessons_learned`; `owner` (FK `AUTH_USER_MODEL`, `SET_NULL`) + `owner_label`; `affected_services` (M2M to `core.ServiceComponent` — a real M2M, and the auto-generated through table is not a hand-declared model, so this does not break the four-model cap); `evidence` (free text, same shape as everywhere else); `notes`; created_at / updated_at. Indexes: `(tenant, -discovered_at)`, `(tenant, status)`, `(tenant, incident_class)`, `(tenant, is_notifiable)`.
- **The derived deadline is the model's whole reason to exist, and it is also its sharpest edge.** `regulatory_deadline` must be a **property computed from `discovered_at`**, never a typed field, for exactly the reason 0.16 made `Incident.resolved_at` derived in `save()`: the two can then never disagree. The board's honest move is to render `is_notifiable is NULL` as **"decision outstanding — the clock is running"**, not as "no" and not as "not applicable".
- **Relates to:** FK `tenant`, `incident` → `core.Incident`, `primary_threat`, `owner`; M2M `affected_services`. **No FK to `core.AuditLog`**, and — the important one — **no second tamper-evidence mechanism**: `procurement.AuditSeal` (6.17) already chains SHA-256 digests over a range of `core.AuditLog` ids, and that is NavERP's tamper-evidence story. 0.18's `forensic_log` is a narrative; the *seal* over the record is 6.17's, and 0.18 should link to it in prose rather than re-implement it (§4).

### Pages implied by the 4 models (for the todo agent, not a build order)

`SecurityThreat` list/detail/form · `IpAccessRule` list/detail/form · `VulnerabilityFinding` list/detail/form · `SecurityIncident` list/detail/form · plus **three computed boards, no models**: a **threat board** (`SecurityThreat` by state and severity, with the *"zero rule"* — an empty board must not render as "no threats", only as "none recorded"), a **vulnerability board** (open findings by CVSS band, overdue count, and the `fix_available=no` count), and a **breach-clock board** (open security incidents with `is_notifiable NULL` and hours remaining). Plus a **brute-force correlation board** reading `accounts.LoginAttempt` (0.18 declares nothing for it — it is a query, not a table). The 0.8 `retention_board`, 0.13 `integration_board` and 0.17 `health_board` / `firing_board` / `capacity_board` are the precedents, and 0.17's `alertevent_acknowledge` / `alertevent_resolve` POST-only actions are the precedent for a `securitythreat_triage` / `securitythreat_resolve` pair.

## 3. Explicitly deferred / not built

Each of these is a NavERP.md word that a naive build would turn into a table. Every one is declined **for a stated reason**, in the same spirit as 0.17's §3.

- **A second log store, log shipping, or a real SIEM index** (bullets 3, 5) — `core.AuditLog` already exists and is a **different subject** (who changed which row, not what an adversary did); a `SecurityLog` / `LogEntry` / `EventIngest` table would be both the L36 parallel-schema violation **and** a table nothing writes to, which is the 0.16 "reports success while nothing happened" lie. `config/settings.py` has no log collector and `requirements.txt` has no shipper. **Add when a log pipeline is actually deployed.**
- **Forensic *logging* as a pipeline** (bullet 3) — 0.18 serves the bullet's *honest* half: `SecurityIncident.forensic_log` is a **narrative a person writes** about what was found and preserved. A chain-of-custody **artifact table** (evidence id, custodian, `acquired_at`, hash, storage location, action log) is declined: NavERP acquires nothing, so every row would be fabricated. **This is the same deferral 0.17 made for "centralized log shipping", and it is deliberate, not an oversight.** *Trigger to revisit:* the moment NavERP stores a binary artifact with a hash.
- **Live SIEM / SOC integration** (bullet 5) — no exporter, no syslog forwarder, no HEC endpoint, no Splunk / Sentinel / Elastic client anywhere. #22 is served as a **recorded connection row** (connector name, format, last-synced note), not as a shipping pipeline. `core.ConnectorDefinition` (0.13) already owns the connector vocabulary if one is wanted; 0.18 must not re-declare it.
- **"Real-time" alerting** (bullet 5) — there is no scheduler, no event bus and no queue. Every alert in NavERP is a row a person wrote. The word is declined on the page rather than approximated.
- **CAPTCHA / bot-challenge integration** (bullet 4) — no `captcha` library in `requirements.txt`, no Turnstile or reCAPTCHA key handling, no challenge issuance, and no field to store a response. `IpAccessRule.action` carries the *challenge vocabulary* (Cloudflare's own action names) as a **recorded posture**. **Declined, not stubbed**: a CAPTCHA widget that never validates is worse than no widget.
- **WAF integration / managed rulesets** (bullet 4) — NavERP has no WAF in front of it and no proxy layer; `apps/core/middleware.py` holds only `TenantMiddleware` and `SessionTimeoutMiddleware`. A `WafRule` / `Ruleset` model would describe a system that does not exist. `SecurityThreat.rule_reference` + `waf_action` carry the *reference* a finding would have.
- **Rate-limit **enforcement** / a gateway** (bullet 4) — `core.RateLimitPolicy` says in its own docstring that *"Nothing enforces it — there is no gateway process."* 0.18 does not change that sentence. It adds the **observation** layer only (§0.1). No token bucket, no `429`, no middleware.
- **Patch *execution* and a patch scheduler** (bullet 2) — `due_on` and the SLA constant are a **recorded policy**; no scheduler runs them. 0.20 owns the scheduler (NavERP.md 0.20: *"Job Scheduler & Background Tasks — cron jobs, queue management, and batch-process monitoring"*). 0.18's docstring repeats the `SyncSchedule.frequency` / `AlertRule.frequency` / `BackupJob.frequency` sentence verbatim in spirit.
- **Vulnerability **scanning** as an executed action** (bullet 2) — no scanner, no CI, no agent. `VulnerabilityFinding` is a register of findings somebody obtained and recorded. There is no `scan_run` model and no `ScanJob`.
- **Brute-force **lockout** / account throttling** (bullet 1) — this is `accounts`' territory (0.2/0.3) and it is already partly there: `accounts.LoginAttempt` + `apps/accounts/security.py::risk_score()` + `RISK_STEP_UP_THRESHOLD`, whose own comment says a user without a second factor *"is flagged but never blocked — silently locking someone out on a heuristic would be worse than the risk it guards against."* 0.18 adds **no** lockout counter, **no** `locked_until`, and **no** write to `accounts`. It reads those rows on a board.
- **An asset / host / attack-surface inventory** (bullets 1, 2) — the single biggest reason #26 (attack path) and #21 (real WAF targeting) are deferred. `core.ServiceComponent` is a *watched thing with a status*, not an inventory of hosts, IPs, accounts and cloud resources. 0.18 FKs it and does not extend it.
- **An IOC / indicator table with STIX/TAXII export** (#28) — a real IOC table is a product feature that arrives with a real feed. Without one it is a text field on the finding, which is what `evidence` is.
- **Virtual patching as an automatic compensating control** (#29) — declined for the same reason as everything above: nothing deploys a patch here.
- **Attack-path / exposure graph** (#26) — needs the asset inventory just declined.
- **Escalation, on-call, paging and notification routing** — 0.11 owns escalation (`SlaRule` / `ApprovalLimit`) and 0.12 owns channels and routing (`NotificationRule` / `Channel` / `Template` / `ProviderConfig`). 0.18 declares none of it and adds **no** notification FK; a security incident that needs a page out uses 0.12's route.
- **A second incident lifecycle or a second postmortem model** — `core.Incident.incident_type="postmortem"` is **reserved and unused**, and 0.21 owns postmortems. `SecurityIncident` has its own NIST lifecycle; it does not re-declare 0.17's, and it does not claim the `postmortem` value.

## 4. L36 ownership calls, and the risk of overlap

**L36 — never re-declare a sibling's spine. 0.18 is a security register *over* the existing spine, not a second spine.** The six calls, each decided before any code is written:

1. **No second rate-limit table.** `core.RateLimitPolicy` (0.13) owns the limit. 0.18 FKs it (`SecurityThreat.rate_limit_policy`, `IpAccessRule.rate_limit_policy`) and **adds no column to it, no migration to `Integration.py`, and no re-export edit to that file.** Full reasoning in §0.1.
2. **No second alerting engine, and no new columns on a 0.17 model.** `AlertRule(category="security")` + `core.AlertEvent` is the whole seam, and it is a **committed contract** (`test_monitoring_security_is_the_018_seam`). `SecurityThreat` carries `mitre_technique` and `source_ip` because `AlertEvent` deliberately does not and `Monitoring.py` refuses to grow. Full reasoning in §0.2.
3. **No second audit log.** `core.AuditLog` is *who changed which row*; a security finding is *what an adversary did*. Different subject, different evidence — L36, not a merge. Forensics are a narrative on `SecurityIncident`, not a log.
4. **No second incident lifecycle.** `core.Incident` stays the availability/comms artifact; `SecurityIncident` FKs it and adds the NIST lifecycle + the regulatory clock. Two *different* enums is correct here, because forcing a breach into 0.17's `scheduled` / `monitoring` / `verifying` union would be the L36 bug in the other direction.
5. **No second notification, escalation or scheduler vocabulary.** 0.12 owns delivery, 0.11 owns escalation, 0.20 owns the scheduler, 0.13 owns the connector vocabulary. 0.18 FKs none of them and re-declares none of them; `SyncSchedule.FREQUENCY_CHOICES`, `AlertRule.SEVERITY_CHOICES` and `BusinessRule.OPERATORS` are reused **by reference** where a vocabulary is needed, each with the same `is`-identity test 0.17 already commits for two of its three.
6. **No second vulnerability or compliance spine.** `procurement` 6.17 owns *supplier* compliance; 0.18 owns *platform* security. Distinct subjects, distinct apps, no overlap on any table.

**The one genuine adjacency: `procurement.AuditSeal` and forensic evidence.** 6.17's `AuditSeal` is *"A SHA-256 seal over one id-keyed range of this workspace's `core.AuditLog`"*, chaining `chain_digest = H(prev_digest : digest)`, with no edit route and no delete route. **That is already NavERP's tamper-evidence mechanism over the audit trail.** So:

- 0.18 must **not** add a hash, a chain, or a seal column to anything. A second tamper-evidence mechanism is a parallel schema for the same concept — the exact L29 / L36 shape.
- `SecurityIncident.forensic_log` is a **narrative**; the *integrity* of the underlying `AuditLog` range is 6.17's, and 0.18's page should point at `procurement`'s seal register in prose rather than re-implement or duplicate it.
- **L36 action required in the same pass as the build:** when 0.18 ships, `NavERP-ERD.md` and `NavERP.md` should be edited so **both** rows agree — 0.18's row gains the four models and says it *extends* `core.RateLimitPolicy`, `core.AlertRule`, `core.AlertEvent`, `core.Incident` and `accounts.LoginAttempt` by FK; procurement 6.17's row notes that the seal is the integrity layer over `core.AuditLog` and that 0.18's forensic field is narrative only. Editing only 0.18's row leaves the doc contradicting the code, which is what L36 §2 forbids.

**Boundary vs 0.19 License & Subscription Administration.** NavERP.md 0.19 bullet 3 is *"Usage Metering & Quotas — consumption tracking, overage alerts, and fair-use limits"*. `RateLimitPolicy.max_requests` is a **security / abuse** bound on requests; `tenants.UsageRecord.included_allowance` is a **commercial** bound. **Ruling: 0.19 owns the quota; 0.18 owns the abuse bound and the evidence of breaching it.** They are different facts about the same number and 0.18 must not add a `quota` or `overage` field. Flag this in `NavERP-ERD.md` in the same pass (L36: reconcile for **both** modules).

**Boundary vs 0.20 Admin Console & System Operations.** 0.20's bullet 1 is *"Unified Admin Dashboard — central command center for users, security, health, and configuration"*, so 0.20's dashboard must **link to** 0.18's threat board and breach-clock board, not re-declare security. 0.20's bullet 2 owns the **scheduler** 0.18 declines; its bullet 3 owns maintenance windows and change management, which is where 0.18's `due_on` remediation windows would be *executed* — 0.18 records the date, 0.20 owns the window.
